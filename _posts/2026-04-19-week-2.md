**User Account Concepts**

Three types of accounts exist in Linux: system, service, and user accounts.
System accounts represent parts of the Linux operating system itself. Various Linux components have access to different resources, and that access is managed based on system accounts.\

Service accounts allow applications to access system resources, such as central processing unit (CPU) time, memory, and networking. For example, the Apache web server service (httpd) needs to consume system resources to provide web pages to external clients. Linux grants (and limits) the required privileges for Apache's service account.
System accounts: Accounts critical to the running of the operating system. These have a user identification (UID) range of 1-4, as UID 0 is reserved for root.\

Service accounts: Accounts necessary for the operating system, applications, and services. These usually have a UID range of 100-999, though the exact range varies by distribution.
User accounts: Accounts that represent people authenticating to the system to access resources. These have a UID range of 1000 and upward. This may vary by distribution.
Two files store user account data: /etc/passwd and /etc/shadow. Note that both of them reside in the /etc directory, where most Linux configuration files reside. The /etc/passwd file stores the actual user accounts and many of their settings. The /etc/shadow file stores password information for the accounts. It also contains account expiration information.\

Username: The name the user logs into the system with.
Password: User password represented as an x; the actual password is stored in the /etc/shadow file.
User ID: Unique number representing the user to the system.
Group ID: Unique number representing the user's primary group.
Comment: Typically displays the user's full name but may store any needed value.
Home directory: Absolute path to the user's home directory.
Login shell: Absolute path to the user's default shell (usually /bin/bash).\

The useradd command creates users, while usermod modifies existing users and userdel removes existing users. Many Debian-based distributions recognize these commands, but they also support the adduser and deluser commands.
Some common options for the useradd command include:\

-c Sets the comment value, usually the user's full name.
-e Sets the expiration date for the user account, in the format YYYY-MM-DD.
-m Creates a user home directory in /home.
-s Sets the user's default shell.
-u Sets a specific user ID value.
-D Displays the default settings.


The syntax for using useradd is useradd -options argument.\

For example, if you are creating a new user account for a user named Kai Garcia whose account will expire on December 31, 2030, and you know that Kai prefers the Korn shell, the command will look like this: useradd -c "Kai Garcia" -e 2030-12-31 -s /bin/ksh kgarcia.

The useradd command creates the user but does not set a password. Most Linux systems will not allow users to log in with a blank password, so even though the account exists, it is not yet usable. The passwd command sets passwords for user accounts.\

The syntax for using the passwd command is passwd {username}.
For example, to reset Kai Garcia's password, type passwd kgarcia.\

You must enter a new password twice. Use the passwd command to configure a password for a new account and reset a forgotten password for an existing user.

One way of displaying the contents of the /etc/group is to use the tail command. To do this, type tail /etc/group.

**Privilege Escalation Concepts**\

Avoiding signing in as the root user is an example of the principle of least privilege. This principle states that you should grant the minimum level of access necessary to accomplish a given task.
The su utility allows users to "switch user" to another account. 
The syntax for using su is su {username}.
For example, to switch to the root user, type su root.

**Editing With visudo**

The /etc/sudoers file is a normal text file, but it is important not to directly edit it with a standard text editor like Vim or nano. The /etc/sudoers file controls access to all elevated privileges, and a mistake in this file can render it impossible for anyone to gain root privileges on the server.\

Most distributions will set a default editor (usually Vim or nano) for /etc/sudoers. When using the visudo command, the system verifies the syntax of the /etc/sudoers file before committing changes, allowing the administrator to correct mistakes before they become part of the running configuration.\

The following are some options you can use with the visudo command:\

-c Checks the existing /etc/sudoers file for errors.
-f Edits or checks a /etc/sudoers file in a different location than the default.
-s Checks the /etc/sudoers file in strict mode—any aliases used before being defined will result in errors.
-x Outputs the /etc/sudoers file to the specified file in JavaScript Object Notation (JSON) format.
​​​The ​/etc/sudoers​ file recognizes four aliases that make it easier to configure and delegate by grouping together users, commands, or other entities. These four aliases are:\

​​User_Alias​ Users who can execute one or more commands.
​​Cmnd_Alias​ Commands that users can run.
​​Host_Alias​ Computers where users can run commands.
​​Runas_Alias​ ​​Alternate username under which the command runs (usually root).\

Members of the wheel group exercise the administrative privileges of root with less potential for damaging the system.
Remember to use the visudo command to edit the privileges of the wheel or sudo group, if necessary.\

The sudo -i command enables a user to simulate full root access, including a new shell with the root user's environment variables loaded. It even changes the current working directory to the root user's home directory at /root. This delegation should be rare and well thought out, as it offers extremely broad privileges on the system.
Administrators can add the # includedir /etc/sudoers.d line to the main /etc/sudoers file, directing sudo to check the sudoers.d directory for additional configuration information. Admins can then add files to this directory with more detailed and robust privilege delegations.\

Some Linux files require root user privileges to edit. You can accomplish this with a sudo configuration, but a simpler and more secure option is to use the sudoedit command. This command allows users to edit a file with their own credentials, even if the file is only available to the root user. Using sudoedit also lets the user edit the file with their preferred text editor.\

To use sudoedit, you must make an entry in the sudoers file. For example, you could add the following line to the /etc/sudoers file: %editors ALL = sudoedit /path/to/file.
The sudo configuration is appropriate for commands that need to be executed with elevated privileges, while the sudoedit option is appropriate for files that you must edit with elevated privileges.\

**Policy Kit Rules**

The polkit (PolicyKit) toolkit provides a different way of delegating privileges than sudo. The polkitd daemon works with systemd to assign more granular control to users than sudo allows. Unlike sudo, polkit does not grant full root access to a process. Instead, it grants specific access to defined actions.\

Write rules that define what actions can be performed by what users. The actions, or specified processes, are written into text files. The rules are also text files that reference the actions. Default rules exist, and administrators can modify these rules. Actions are defined in XML files stored at /usr/share/polkit-1/actions. These files have a .policy file extension.\

Rules files are stored in two different directories: /etc/polkit-1/rules.d for local policies and /usr/share/polkit-1/rules.d for third-party policies. You will find individual rules files within these directories. Rules files use a .rules file extension.\

Four commands are associated with polkit. These commands display details and authorization information, or enable a user to execute a command with elevated privileges.\

pkexec Allows an authorized user to execute an action.
pkaction Displays details about an action.
pkcheck Displays whether a process is authorized.
pkttyagent Provides a text-based authentication agent.\

Scenario 2: sudo\

A user calls and says sudo is broken on their system after they edited the /etc/sudoers file with nano. The user wants you to fix it.
Open /etc/sudoers with visudo and allow it to identify syntax errors that nano would not have caught. Let the user know to use visudo in the future.\

Scenario 3: Authorization\

A user indicates they cannot accomplish administrative tasks for which they are authorized.
The likely problem is that they are not a member of the wheel group or have not been delegated the tasks directly in the /etc/sudoers file. The easiest solution is to add them to the wheel group.\

Scenario 4: New Command/

A user calls after attempting to run a command referenced on an Internet website. The user preceded the command with sudo and pkexec, as suggested on the site. However, the command failed to run.
The likely problem is that the privilege has not been delegated via either sudo or polkit.
